# Source snapshot transfer design

Status: implemented for v0.4.0, pending release validation. Sharebox v0.3.0 does not transfer source files.

The intended workflow is for an LLM with local filesystem access to upload the
current project once, receive an immutable snapshot ID, and submit approved test
tasks against that ID. A worker must verify the snapshot before execution, and
each result must identify the input snapshot. This is source transfer, not chat
history sharing or arbitrary access to the worker filesystem.

## Trust boundary

The user has explicitly requested source transfer. Existing local-checkout tasks
remain unchanged and must reject snapshot inputs unless their owner opts in.
Fixed task arguments do not make uploaded source safe: a test file or package
script can execute code. A separate working directory is not a sandbox.

Both Docker isolation and explicitly trusted native execution are owner-configured modes. No existing worker gains permission to execute uploaded code implicitly; configuring a snapshot task is a separate owner decision.

## Immutable input

- Versioned manifest of relative paths, byte sizes, SHA-256 digests, and an
  executable flag. Canonical ordering makes snapshot identity deterministic.
- Stage file bytes locally once. Hash and upload those staged bytes rather than
  rereading a changing developer checkout after calculating its digest.
- Initial limits: 4,096 files, 16 MiB per file, 128 MiB total, and a 512 KiB
  manifest. Application chunks are at most 256 KiB and remain below the existing
  HTTP body limit. No untrusted tar/zip extraction is needed.
- Respect ignore rules and always exclude credentials, dependency directories,
  VCS metadata, and build caches. Never transfer `node_modules` across platforms.
  Filtering does not guarantee that ordinary source lacks hardcoded secrets.
- Reject traversal, absolute paths, symlinks, reparse points, special files,
  hard links, case collisions, and file/directory collisions. The initial portable
  filename policy is ASCII-only, including Windows reserved-name restrictions.

## Ownership and persistence

Uploads must be bound to an authenticated principal, not merely anyone who knows
a content hash. Every chunk and commit rechecks revocation and quota. Bytes and
acknowledgement metadata must be durable before reporting success. A snapshot is
published only after all file hashes and the manifest are verified.

Workers may download input only for a job assigned to that worker. Downloads
must recheck assignment, active status, and the exact snapshot. Job idempotency
must include snapshot identity, so a repeated request key cannot silently refer
to different source. Cancellation, heartbeats, and leases must cover transfer and
dependency preparation as well as the final test process.

No client-provided host path, shell command, Docker flag, credential, or working
directory will be accepted. Workspaces are generated by the worker. Immutable
input caches are separate from disposable run directories; cleanup must preserve
snapshots referenced by queued or active jobs.

## Execution and scale

The same verified input can be sent to several workers. Dependencies can be installed
on each target platform using the uploaded lockfile and an owner-approved setup
step. Dependency caches are not implemented in v0.4.0; future caches must account for lockfile, runtime, platform, and architecture.
Source distribution is a prerequisite for useful parallel tests; it does not by
itself implement test discovery, sharding, artifact collection, or scheduling.

Docker execution uses owner-configured images, commands, resource limits,
and networking. It must not mount credentials or the Docker socket, use privileged
mode, or accept caller-controlled host mounts. Native execution requires an
explicit owner acknowledgement that uploaded code runs with the worker account's
permissions. Neither mode is enabled for an existing task merely by upgrading Sharebox.
